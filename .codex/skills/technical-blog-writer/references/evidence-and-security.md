# AI 与安全博客取证协议

用于新闻综合、软件版本比较、评测解读和漏洞分析。按选题使用相关字段，
不要为不适用的字段制造数据，也不要让取证表代替正文解释。

## 1. 论点与证据台账

| 字段 | 记录内容 |
| --- | --- |
| 论点 | 一句可证伪的事实、比较或判断；拆开复合论断 |
| 证据类别 | 官方声明、代码行为、实测、社区观察、推断 |
| 原始位置 | URL、标题、作者/机构、发布日期/更新日期、章节/表格/代码行 |
| 访问状态 | 本次打开 / 输入摘录 / 访问失败 / 仅发现线索；访问时间 |
| 决定性材料 | 简短原文、数值、配置、代码行为或实验记录 |
| 推导 | 事实如何支持结论，必要前提、替代解释与反例 |
| 适用范围 | 版本、分支、平台、环境、权限、时间范围 |
| 缺口与处理 | 未披露、冲突、待复现；补查、缩小论点、删除或标记草稿 |

正文应能读到“证据是什么、为什么能这样判断、什么时候不成立”。
仅在末尾列一串资料，或在段尾加编号但来源不支持该判断，均不合格。

## 2. 数据取证

对每个支持核心结论的数字，保留原始值、单位、定义、精确出处和日期。

| 数据类别 | 需要核对的解释条件 |
| --- | --- |
| 模型/工具评测 | 数据集与版本、成功标准、样本/分母、模型和工具版本、运行次数、预算/重试、基线和独立性 |
| 性能/成本 | 硬件、操作系统、并发、输入规模、缓存、统计量、单位与计费时间；均值不能冒充 p95 |
| 事故/攻击统计 | 采集窗口、总体/样本、去重、统计单位；扫描次数、受害者数、受影响资产数不是同一指标 |
| CVSS/漏洞 | 评分版本与发布者、向量（如提供）、受影响/修复版本与条件；利用情况另查公告或 KEV 等证据 |
| 版本/日期/许可证 | 原始公告、tag、清单、LICENSE；不能从项目名或发布时间推测 |

数字缺上下文时可以准确转述“来源报告了 X，但未披露 Y”，不能由此推广
为生产效果或提升幅度。相同计量口径下，从 20% 到 30% 是增加 10 个百分点，
相对增加 `(30 - 20) / 20 = 50%`；两者必须区分。不要合并不同基准的成绩。

## 3. 软件来源与能力变化

先确认分析的是模型、API 服务、SDK、Agent 框架、插件还是完整应用。
模型的知识/推理成绩不等同于应用获得文件写入或网络权限后的系统安全性。

收集：官方维护者及归属依据、仓库/文档/发行渠道、版本/tag/commit、许可状态、
关键依赖和部署环境、输入输出、外部调用、文件/网络/凭证权限。
闭源软件使用官方协议、API、版本公告和可观察行为，明确代码不可核验的边界。

对关键变化做比较：

| 基线 | 当前版本 | 可核实改动 | 证据位置 | 安全含义与限制 |
| --- | --- | --- | --- | --- |
| 已确认的旧版本和行为 | 已确认的新版本和行为 | 新增/删除/默认值/权限/API 变化 | release + diff/协议/实测 | 影响什么资产，何种配置下成立 |

没有旧版材料时只描述当前能力，不把“第一次看到”写成“首次实现”。
存在配置开关时区分默认行为、可选行为和实验能力。

## 4. GitHub 与 linux.do 调查

使用可用的检索/浏览工具；记录实际执行的查询、时间和访问结果。以下是查询
形态示例，`<...>` 必须替换为已知项目/版本，不是已检索过的证据：

- `site:github.com/<owner>/<repo> <version> release permission`
- `site:github.com/<owner>/<repo> <component> security issue`
- `site:linux.do <project> <version> 测试`
- `site:linux.do <project> 权限 安全 问题`

GitHub：由官网反向确认仓库归属，避免同名项目。定位 release/tag 对应的 commit；
按判断需要打开 diff、具体函数/配置、测试、advisory 或 issue。引用已打开的
`blob/<commit>/<file>#Lx-Ly` 等固定位置。测试源码存在不代表本次执行通过。
PR 的建议、合并状态和进入正式发布版本分别核对。Stars 仅可说明关注度。

linux.do：阅读具体主题和有关楼层，记录原作者、时间、测试版本、环境、步骤、
实际结果，以及后续更正或反例（不存在时不要编造）。匿名体验、截图和转载
可以提供线索，但不能独立支持普遍性能或安全结论。顺着外链查看上游材料，
避免把同一厂商公告的多次转载当成交叉验证。

访问失败、登录限制或无相关结果时记录实际状态，继续使用已核实的一手材料。
平台覆盖不应压过证据质量；不要绕过访问控制或凑出不存在的帖子。

## 5. 专业安全分析

对中心论点回答相关问题，不要求每篇文章机械填写全部栏目：

- 资产：代码、数据、账号、令牌、供应链或生产服务中的什么需要保护？
- 攻击面：攻击者能控制检索文档、依赖、工具返回、网络输入或用户内容的哪一部分？
- 边界：数据何时被模型解释为指令？工具的身份、授权、对象权限分别在哪里检查？
- 前置条件：版本、配置、认证、网络位置、用户动作、默认/可选权限是什么？
- 机制：输入如何经组件/工具到输出？安全检查在哪一步失效或阻断？
- 影响：哪些版本/资产受到影响？代码显示的是可达路径还是已观察到的事件？
- 缓解：措施阻断哪一环？代价、残余风险与补丁外的配置要求是什么？
- 验证：版本/配置核对、只读检查、隔离测试、预期结果与失败判据是什么？

避免只写“最小权限、加强审计、及时升级”。说明具体权限/日志事件/版本和
验证方法；未执行的步骤标成建议。没有日志或实验就不能写“成功阻止攻击”。

## 6. 交付检查

逐个检查中心论点是否有足够证据、解释和技术细节；重算派生数据；核对标题和
摘要没有超出正文。先删去可有可无的无证据判断，再决定核心缺口是否阻止交付。
证据不足时输出“待补证草稿”，附具体需要打开的材料或可执行的核验步骤。
不要因为缺少 linux.do 帖子就阻止一篇证据充分的官方补丁分析，也不要为了交付
而把社区传闻写成结论。
